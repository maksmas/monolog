# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Monolog is a CLI personal backlog tool written in Go. Tasks are stored as individual JSON files in a git repo for conflict-free cross-device sync. See `docs/plans/completed/20260411-monolog-cli-mvp.md` for the MVP spec.

## Build & Test Commands

```bash
go build -o monolog          # Build binary
go test ./...                # Run all tests
go test ./internal/store/    # Run tests for a single package
go test -run TestCreate ./internal/store/  # Run a single test
go vet ./...                 # Lint
```

### Release & distribution

```bash
make build VERSION=v0.1.0    # build with an explicit version stamped in
make demo                    # regenerate the README hero GIF (needs vhs)
```

- **Versioning**: `cmd.Version` (default `"dev"`, wired into cobra's `Version:` so `monolog --version` works) is injected at build time via the Makefile's `LDFLAGS` (`-X github.com/maksmas/monolog/cmd.Version=$(VERSION)`, `VERSION ?= dev`). `build` and `build-bot-linux` (plus its `-arm64`/`-amd64` aliases) share the same ldflags.
- **Releases**: cut by pushing a `v*` git tag, which triggers `.github/workflows/release.yml` → GoReleaser (`.goreleaser.yaml`, `version: 2` schema). GoReleaser cross-compiles darwin+linux × amd64+arm64 archives + `checksums.txt` onto a GitHub Release, and publishes a Homebrew **cask** (`homebrew_casks:` block) to the `maksmas/homebrew-tap` repo (requires the `HOMEBREW_TAP_GITHUB_TOKEN` Actions secret). macOS users install with `brew install maksmas/tap/monolog` — the cask is **macOS-only** (Homebrew casks are unsupported on Linux, and this one runs a macOS `xattr` quarantine hook); Linux users take the prebuilt binary or `go install`.
- **Demo GIF**: the README hero (`docs/img/demo.gif`) is generated from `docs/demo.tape` via `make demo` (requires charmbracelet `vhs`). The tape isolates `MONOLOG_DIR` to a temp dir so a real backlog is never recorded; the rendered GIF is committed as a binary artifact.
- **CI**: `.github/workflows/ci.yml` runs `go build`/`test`/`vet` on push + PR (Go version pinned via `go-version-file: go.mod`).

## Architecture

```
main.go                 → Entrypoint, calls cobra root command
cmd/                    → One file per CLI command (add.go, ls.go, etc.)
internal/config/        → User-facing date-format and theme accessors; Load/Save/SetDateFormat for settings persistence
internal/model/task.go  → Task struct with JSON tags, ULID generation
internal/store/         → File-based CRUD, prefix-match ID lookup, initials resolution, filtering/sorting
internal/ordering/      → Fractional position math and rebalancing
internal/schedule/      → Bucket names ↔ ISO dates, bucket classification, layout-aware Parse/FormatDisplay
internal/recurrence/    → Recurrence-rule parsing, next-occurrence math, shared done+spawn flow
internal/search/        → Pure ranker behind an Index type (NewIndex/Rank/RankTerms/Len), shared by the TUI overlay and `monolog search`
internal/display/       → Terminal table formatting and compact date helpers (layout-aware)
internal/git/           → Git operations (init, auto-commit, sync with conflict resolution); also AutoCommitSHA (stage+commit+return HEAD SHA), headSHA, CommitSubject, Revert, RevertSHA helpers used by TUI undo/redo; AutoPush (autopush.go) plus the repoMu mutex and the shared pullRebaseResolving helper
internal/tui/           → Bubble Tea interactive TUI (default when run with no subcommand)
internal/email/         → Gmail integration: small Gmail interface + real client, OAuth token I/O & refresh, pure Message→Task conversion, batch-commit Sync orchestrator
internal/telegram/      → Telegram bot integration: neutral Bot interface + real tgbotapi client, pure parse/format helpers, long-poll Serve orchestrator with pull ticker and read-only-on-conflict mode
```

Commands in `cmd/` handle CLI parsing and delegate to `internal/` packages. Running `monolog` with no subcommand launches the interactive TUI. Every mutation auto-commits to git and — unless auto-push is disabled — pushes that commit to the remote (see **Auto-push on mutation**): in a background goroutine in the TUI, but **synchronously** in the CLI, immediately after the success line, where a bad network can add a few seconds before the process exits.

## Key Design Decisions

- **One JSON file per task** (`<repo>/.monolog/tasks/<ULID>.json`): eliminates merge conflicts on sync. Two devices editing different tasks rebase cleanly.
- **ULID IDs**: time-sortable, globally unique, users type partial prefixes (e.g. `01J5K`) which resolve via directory scan.
- **Title-initials lookup**: CLI commands (`done`, `edit`, `rm`, `mv`) resolve identifiers via `store.Resolve()`, which tries ULID prefix first, then falls back to matching the first letters of each word in open task titles (e.g. `flb` → "Fix login bug"). Minimum 2 characters, case-insensitive, prefix-matching on initials. Ambiguous matches list conflicting titles. Implemented via `model.Initials()` and `store.Resolve()`.
- **Fractional positions**: inserting between positions 1000 and 2000 gives 1500. Rebalance all positions in a schedule group when any gap drops below 1.0. Default spacing is 1000.
- **Schedule values**: `today` (default), `tomorrow`, `week`, `month`, `someday`, or a date. User-facing input/display format is configurable via `internal/config` (`DateFormat()`, `DateFormatLabel()`, `DateRegex()`); default is `DD-MM-YYYY` (`"02-01-2006"`). `schedule.Parse(input, now, layout)` accepts bucket names, input in the passed layout, and legacy ISO (`2006-01-02`) silently so pre-existing scripts keep working. `schedule.FormatDisplay(iso, layout)` renders a stored ISO date back to the configured layout at display time. On-disk `schedule` JSON stays ISO regardless of `DateFormat` — no migration when the display format changes. Callers pass `config.DateFormat()` through to `schedule`/`display`/`model` helpers; those packages never import `internal/config` directly, which keeps them easy to test with arbitrary layouts. **Relative shorthands** (`Nd`, `Nw`, `Nm` — e.g. `3d`, `2w`, `1m`) are handled by `schedule.ParseRelative(input string, now time.Time) (string, bool)`, which the TUI `updateReschedule` calls before `schedule.Parse`; on a match it returns an ISO date directly without touching `schedule.Parse`'s signature or behavior.
- **Runtime data directory**: `~/.monolog/` by default, override with `MONOLOG_DIR` env var.
- **Active tasks**: the reserved `active` tag marks tasks in the current working set. Active tasks render in green in the TUI and appear in a dedicated panel above the tab bar. `done` auto-deactivates; `edit --tags` preserves active state.
- **Auto-tag from title prefix**: when creating a task, if the title starts with `"tagname: ..."` and `tagname` is a tag that already exists on another task, it is automatically added as a tag. Title is kept as-is. The reserved `active` tag is excluded. Implemented via `model.ParseTitleTag()` and `model.CollectTags()`.
- **Tag view mode**: the TUI has two view modes (`viewSchedule` / `viewTag`), toggled with `v`. In tag view, tabs become tags (active first, alphabetical middle, untagged last), each showing tasks grouped by schedule bucket with separator items. Grab mode in tag view restricts movement to within a single tag tab (no left/right). Launch directly into tag view with `monolog --tags` / `-T`.
- **CompletedAt lifecycle**: `Task.CompletedAt` (RFC3339, omitempty) is set when `doneSelected()` fires. It is never cleared (tasks cannot be reopened today). Existing tasks without `CompletedAt` are excluded from avg-time-to-complete calculations. Used by `model.ComputeStats()`.
- **Stats bar**: the TUI always shows a one-line stats bar (total/open/done/in-tab/avg) above the tab bar. Stats are cached in `Model.stats` (a `model.Stats` value) and refreshed via `reloadAllTasks()` at the end of every `reloadAll()` call. `model.ComputeStats([]Task, time.Time)` and `model.FormatDuration(days float64)` in `internal/model/stats.go` are pure functions, easily unit-tested.
- **Tag autocomplete**: both the add-task and retag modals show inline autocomplete suggestions as the user types in the tag field. `model.FilterTags(known, field)` is a pure function that extracts the fragment after the last comma, filters known tags by case-insensitive prefix, excludes already-entered tags, and caps at 5 results. Suggestions are navigated with Up/Down, accepted with Tab/Enter (replaces fragment and appends `", "`), and dismissed with Esc. State lives in `Model.suggestions`/`Model.suggestionIdx`, shared between modals since only one is open at a time. The add modal's Recur field reuses the same suggestion plumbing via the pure `recurrence.Suggest(input)` function and shows a static grammar hint line (`recurrence.GrammarHint`) under the input — on the Recur field only **Tab** accepts a suggestion (replacing the full value, since recurrence is a single value) while **Enter** always submits the modal; the same `GrammarHint` is also prepended as a `#` comment header in the TUI YAML edit buffer and referenced in the `--recur` CLI help on `add`/`edit`.
- **Task notes**: notes are stored as timestamped entries appended to the existing `Body` field using `--- <date> HH:MM:SS ---` separators, where `<date>` is rendered in the configured `config.DateFormat()` (default `DD-MM-YYYY`) — no schema migration needed. A `NoteCount int` field (JSON `note_count`, omitempty) tracks the count for fast badge rendering (`[N]` in the task list) without body parsing. `model.AppendNote(body, text, now, layout)` formats and appends note text; `model.CountNotes(body, dateRegex)` only recognizes separators whose date fragment matches the passed regex. Callers build the regex from `config.DateRegex()`. **No backward compat** on the separator regex: changing the configured format loses the `[N]` count contribution from notes written under the old format (stored text is untouched). `NoteCount` is recalculated from `Body` inside both `Store.Create` and `Store.Update` via `model.CountNotes()` — the store layer is the single source of truth, so any path that writes a task (new or existing, including recurring-task spawns whose body already carries the `Spawned from` note) keeps the count consistent without caller bookkeeping. CLI: `monolog note <id> "text"` adds a note, `monolog show <id>` prints full task detail.
- **Detail panel**: pressing `Enter` in the TUI toggles a right-side panel showing task metadata (title, schedule, tags, dates) and the full body with notes. An inline textarea at the bottom accepts new notes (`Enter` submits, `Alt+Enter` inserts a newline, `Esc` closes the panel). Navigating tasks with `Up/Down` while the panel is open refreshes its content. Panel width is ~45% of the terminal.
- **Fuzzy search**: `/` in TUI normal mode opens a full-screen search overlay that fuzzy-matches across both title and body of all tasks (open and done), powered by `github.com/sahilm/fuzzy`. Title matches are weighted 2x over body matches. Enter commits to the selected task, switching `activeTab` to the target bucket/tag and focusing the task; Esc cancels with no side effects. The pure ranker no longer lives in `internal/tui` — it is `internal/search/rank.go`, shared with the `monolog search` CLI command (see **Shared search ranker** below); overlay UI stays in `internal/tui/search.go`, which holds a `*search.Index` in `searchState` and consumes `Result.TitleHit` offsets in `highlightMatches`.
- **Recurring tasks**: `Task.Recurrence string` (JSON `recurrence,omitempty`) holds a rule in one of four forms — `monthly:N` (1..31, clamped to month-end for short months), `weekly:<day>` (accepts three-letter `mon|tue|...|sun`, full names `monday|...|sunday`, or numeric `1..7` with Mon=1, all case-insensitive), `workdays` (Mon-Fri), or `days:N` (N days after completion). Parsing and next-date math live in `internal/recurrence/` (`Parse(string) (Rule, error)`, `Canonicalize(string) (string, error)`, `Rule.Next(time.Time) time.Time`, `Rule.String()`); `Rule.String()` emits the canonical form (`weekly:mon`, `workdays`) so alias inputs round-trip through edit to canonical storage. All three callers (`cmd/add`, `cmd/edit`, and the TUI add modal / YAML editor) validate-and-normalize through `recurrence.Canonicalize`. Spawn is driven by `recurrence.CompleteAndSpawn(s *store.Store, task *model.Task, now time.Time, w io.Writer, dateFormat string)` (shared by `cmd/done.go` and the TUI `d` key), where `w` receives any spawn-warning messages and `dateFormat` is the configured user-facing layout passed in from `config.DateFormat()`. When a completed task has a non-empty `Recurrence`, a new task is created with a fresh ULID, copied Title/Body/Source/Recurrence, tags minus `active`, `Schedule = Rule.Next(now)` (stored ISO); the old task receives the done-state transition AND the back-reference note in a single `Store.Update`, and both files are committed in one git commit whose message formats the next date with `dateFormat` (e.g. `"done: <title> (recurring, next 25-04-2026)"` under the default). Bidirectional cross-references: the new task gets a `"Spawned from <old-ULID>"` note, the old task gets a `"Spawned follow-up: <new-ULID> (scheduled <date>)"` note formatted in `dateFormat`. Stop semantics are edit-based — clearing `Recurrence` (CLI `--recur ""` or removing the `recurrence:` line in the TUI YAML editor, which now exposes it through `editableFields`) before completing prevents the next spawn; there is no SeriesID or series concept. Any spawn failure (invalid stored rule, list/create error) is warned to the caller's stderr and skipped while the underlying completion still succeeds — the repo is never left with an uncommitted half-spawn. CLI surface: `--recur` flag on `add` and `edit`; TUI surface: a third input `addFocusRecur` in the add modal and a `recurrence` line in the YAML editor. **Visibility**: recurring tasks render a `[↻]` marker in the TUI list-item description line (right after the `[N]` notes badge in `item.Description()`), and the detail panel adds a `Recur: <rule>` line between the `Schedule:` and `Tags:` lines (`Model.detailPanelView`). Both are conditional on `Recurrence != ""`; done recurring tasks keep the marker because the source task retains its rule after spawn.
- **Clickable URLs (TUI)**: the TUI wraps `http://` and `https://` URLs in OSC 8 terminal hyperlink escapes so Cmd/Ctrl-click on a visible URL opens the browser. The pure `display.Linkify(s string) string` helper (`internal/display/links.go`) detects URLs with `https?://\S+`, strips trailing punctuation (`.,;:!?)`) so sentence punctuation stays outside the link, and wraps each match as `\x1b]8;;<URL>\x1b\\<URL>\x1b]8;;\x1b\\`. OSC 8 sequences are zero-width so `lipgloss` column math is unaffected, and styling composes cleanly. Integration points — always applied post-wrap / post-truncate on the final visible fragment so escapes never dangle across a cut: the detail-panel title header, the detail-panel body lines, and the task-list title column. **Contract for new render paths**: any caller applying `display.Linkify` to width-constrained output must first pass the text through the URL-aware pre-processors (`wrapTextPreservingURLs` for wrapping, `truncateTitlePreservingURLs` for truncation, both in `internal/tui/model.go`; `display.FindURLSpans` for custom layout logic) so a URL is never split across the visible fragment — otherwise Linkify's regex would see a truncated match and the OSC 8 target would point at a broken URL. `vlist.itemHeight` must mirror whichever wrap helper the renderer uses so row-height prediction stays aligned with rendered output. `MONOLOG_NO_LINKS=1` is an escape hatch that turns `Linkify` into a no-op (also covered by tests via `t.Setenv`). Terminals without OSC 8 support render URLs as plain text — no regression. CLI output (`monolog show`, `monolog ls`), the fuzzy-search overlay, and the YAML editor intentionally stay plain text.
- **TUI color themes**: named color themes ("default" and "dracula") are selectable via the `"theme"` key in `<MONOLOG_DIR>/.monolog/config.json`; the `MONOLOG_THEME` env var takes precedence over the file. `Theme` struct in `internal/tui/theme.go` holds one `lipgloss.AdaptiveColor` field per color role (chrome: `ActiveBorder`, `ModalBorder`, `Hotkey`, `ActiveTabBg`, `ActiveTabFg`, `TabFg`, `Borders`; task list: `NormalText`, `SelectedText`, `DimText`, `GrabText`, `ActiveNormal`, `ActiveSelected`; search: `SearchDone`, `SearchActive`, `SearchCount`, `SearchMeta`, `SearchPreviewBorder`, `SearchPreviewDim`); the `themes` registry maps names to `Theme` values and unknown names silently fall back to `defaultTheme`. `config.Theme()` in `internal/config/` reads the JSON config file and applies the env-var override. `buildStyles(Theme) tuiStyles` in `tui.go` constructs all lipgloss styles from theme fields (replacing the former package-level `var` block); `initStyles(Theme)` in `model.go` handles task-list item styles; `Model` gains `theme` and `styles` fields used for inline color overrides throughout the render paths. Theme-independent styles (`suggestionBoldStyle`, `suggestionDimStyle`, `searchSelectedStyle`) live as package-level vars in `tui.go`. Both `"theme"` and `"date_format": "02-01-2006"` keys are written by `git.Init` into the initial `config.json` template. **User-authored themes (file-based)**: `internal/tui/theme_load.go` scans `<MONOLOG_DIR>/.monolog/themes/*.json` at startup via `loadUserThemes` and merges them into the package-level `themes` map through `initThemes` — both called from `tui.Run` before the Model is built. Files use snake_case keys (`active_border`, `normal_text`, …) with `{"light": "...", "dark": "..."}` pairs; all 19 fields are required. `bootstrapExampleTheme` creates the themes directory with a single `example.json` (a full dump of `defaultTheme`) the first time the directory is absent — it never overwrites or recreates once the directory exists, so deleting `example.json` is a sticky user choice. Loader rejections (invalid JSON, missing field, empty color value) are printed to stderr with a `monolog:` prefix before Bubble Tea takes over; the TUI continues with whatever loaded cleanly. User files named `default.json` or `dracula.json` are rejected as collisions — built-ins are immutable. If the configured theme name disappears from disk between runs, `newModel` falls back to `defaultTheme` and surfaces `theme "<name>" not found, using default` in the status bar without rewriting `config.json` (restoring the file later brings the selection back automatically). Reload is edit-and-restart — no file watcher.
- **Settings modal**: `,` in normal TUI mode opens a settings overlay (`modeSettings`) backed by `openSettings()` / `updateSettings()` / `applySettings()` in `model.go`. Two rows: date format (DD-MM-YYYY / MM-DD-YYYY / YYYY-MM-DD) and theme. `↑↓` navigate rows; `←→` cycle values; `Enter` saves via `config.SetDateFormat` + `config.Save(repoPath, theme, fmt)` and applies the new theme live by rebuilding `m.theme`/`m.styles`/`m.baseStyles`; `Esc` discards. `config.Load(monologDir string) error` is called in `cmd/helpers.go#openStore` so every command (TUI + CLI) picks up the persisted date format on startup. `config.AllFormats() []FormatInfo` (Layout + Label fields) exposes the ordered format list to the settings UI. `config.Save` does a read-modify-write so unknown config.json keys (e.g. `"default_schedule"`, `"editor"`) are preserved.
- **Undo (TUI)**: `u` / `ctrl+z` in normal mode triggers multi-level undo (last 10 actions) backed by `git revert <sha> --no-edit`. TUI mutations use `git.AutoCommitSHA` (stage+commit+return HEAD SHA) while CLI commands use `git.AutoCommit` (no SHA returned). Every TUI mutation captures the SHA into `Model.undoStack` ([]string, capped at 10, newest last). `undoCmd()` **pops the SHA before launching the goroutine** (prevents a second keypress racing on the same SHA), then calls `git.CommitSubject` to build the status message and `git.RevertSHA` (thin wrapper over `git.Revert` + `headSHA`) to create the revert commit and capture its SHA. `CommitSubject` failure is treated as non-retriable (stale SHA — e.g. after a rebase) and the SHA is dropped. `RevertSHA` failure (e.g. conflict) signals restore via `taskSavedMsg.restoreUndoSHA` so `Update` pushes the SHA back in the main loop — never from inside the goroutine (which would race). Stack is cleared when a sync with a remote completes (rebase may have rewritten SHAs), and also by an auto-push that rebased — including when its retry push then failed; local-only syncs preserve the stack. A grab-move that triggers a rebalance commits **every** file it wrote — the moved task plus each rebalanced sibling — so undo restores the whole bucket's ordering (and, more importantly, `.monolog/tasks/` is never left dirty, which would defer auto-push's rebase forever; `cmd/mv.go#rebalanceAndCommit` is the same pattern on the CLI side).
- **Quick capture (Raycast)**: `cmd/add.go` exposes `--body`/`-b` for setting `task.Body` at create time; `Body` was already on the model with `omitempty`, so empty bodies still drop from JSON. The capture flow itself lives entirely outside the Go binary in `docs/raycast/`: a Raycast script command (`monolog-capture.sh`) shells out to `monolog add "$1" --body "$2" --tags inbox`, and a bookmarklet (documented in `docs/raycast/README.md`) builds two prefilled args from `window.getSelection()` + page metadata, redirects to `raycast://script-commands/monolog-capture?arguments=...`. Selection-aware behavior: title prefills with the selection (truncated to 80 chars) or the page title; note prefills with the full selection plus a URL augmented with a `#:~:text=<encoded selection, 300-char cap>` text fragment so reopening scrolls to and highlights the original passage. Same script services the desktop hotkey case (Raycast's "prefill from selected text") with no URL involved. No daemon, no second binary, no URL-scheme registration in monolog itself.
- **Email integration**: opt-in Gmail import + archive-on-done, off until configured. `internal/email/` owns the integration; `cmd/email.go` registers `monolog email {sync,auth,status}`. `internal/email/` MUST NOT import `internal/config` — values flow in via `config.Email() config.EmailConfig` (`{Enabled, Label, SyncInterval, MaxPerSync, ClientSecretsPath}`) read once by callers (TUI Model, `cmd/email.go`, `cmd/done.go`) and passed by value. Config block is the optional `"email"` key in `<MONOLOG_DIR>/.monolog/config.json` (defaults: enabled=false, label=`"monolog"`, interval=5m, max_per_sync=100, client_secrets_path=`$XDG_CONFIG_HOME/monolog/gmail_credentials.json`). `config.SaveEmail` is the read-modify-write writer that preserves foreign keys; `monolog email auth` flips `enabled=true` after a successful OAuth flow. **OAuth**: scope `gmail.modify` (smallest scope covering list/read/label-modify); `Authorize` runs a local `127.0.0.1:0` redirect-callback `http.Server` against the user's downloaded Desktop-app client-secrets JSON; tokens persist as `0600` JSON outside the git repo at `$XDG_CONFIG_HOME/monolog/gmail_token.json` so OAuth secrets never sync across devices. `HTTPClient` wraps a `oauth2.TokenSource` with `persistingTokenSource` so refreshed access tokens get written back to disk. `email.IsAuthMissing(err)` discriminates the no-token case for friendly status output. **Gmail abstraction**: `type Gmail interface { ListLabeled(ctx, label) ([]string, error); Get(ctx, id) (*Message, error); ArchiveLabel(ctx, id) error }` with neutral `Message{ID, Subject, From, Snippet}` DTO so tests fake the interface and the rest of the codebase never imports `google.golang.org/api/gmail/v1`. `realGmail` wraps `*gmail.Service`; `ListLabeled` paginates exhaustively preserving Gmail's newest-first order; `Get` uses `format=METADATA, metadataHeaders=[Subject,From]` (snippet comes for free); `ArchiveLabel` calls `users.messages.modify(removeLabelIds=["INBOX"])` and intentionally keeps the trigger label (option A — archive only). **Conversion** (`convert.go`, pure): `ToTask(*Message, time.Time) (model.Task, error)` strips chained `Re:`/`Fwd:`/`Fw:` prefixes via `(?i)^((re|fwd?|fw):\s*)+`, falls back to `"(no subject)"`; sender via `net/mail.ParseAddress`, falls back to `"unknown"`; snippet HTML-unescaped and rune-capped at 200 with `…` only when truncation occurs; body = `"From: <name>\nhttps://mail.google.com/mail/#all/<msg-id>\n\n<snippet>"` (URL omits `/u/0/` so it works for any signed-in account; no trailing blank lines when snippet empty); tags=`["email"]`; schedule=today; Source=`"gmail"`; SourceID=msg.ID; fresh ULID per call. **Sync** (`sync.go`): `Sync(ctx, gmail, store, repoPath, SyncOptions{Label, MaxPerSync, Now, Writer}) SyncResult{Created, Err}`. Algorithm: (1) `gmail.ListLabeled` (newest-first), (2) build dedup set from `store.List(ListOptions{})` (no Status filter → spans open+done) of SourceIDs where `Source=="gmail"` — completed-and-archived emails self-suppress, (3) filter to new IDs preserving order, (4) take first `MaxPerSync` (remaining silently deferred to next run — soft cap), (5) per-msg Get→ToTask→Store.Create (failures warn-and-continue), (6) **single** `git.AutoCommit(repoPath, "email: imported N task(s) (label=<label>)", files...)` if any created — no commit when zero. **Archive on done**: after `recurrence.CompleteAndSpawn` + `git.AutoCommit`, both `cmd/done.go` (CLI, 5s ctx timeout, fire-and-forget) and TUI `doneSelected` (via `archiveEmailCmd`) call `gmail.ArchiveLabel(ctx, sourceID)` when `task.Source=="gmail"` && `task.SourceID!=""` && email enabled. Archive failure is NON-FATAL: warn-and-continue, task stays done. CLI uses a swappable `var archiveFn = realArchive` seam for testing; TUI swaps via the `Gmail` interface. **TUI integration**: Model gains `emailEnabled`, `emailSyncing`, `emailLabel`, `emailMaxPerSync`, `emailInterval` (no `emailLastErr` — flash messages reuse the existing status-bar mechanism). `Init()` returns `tea.Batch(emailSyncCmd(), emailTickCmd(interval))` when enabled (initial sync IS the first tick); ticker is `tea.Tick`-based and self-rescheduling on every `emailTickMsg`. `s` in `updateNormal` dispatches `tea.Batch(gitSyncCmd, emailSyncCmd())` when enabled. `emailSyncResult{Created, Err}` flashes `"email: N imported"` / `"email sync: <err>"` and, when `Created>0`, calls `reloadAll()` and dispatches the auto-push (see **Auto-push on mutation**). `archiveResult{Err}` flashes `"email archived"` / `"archive failed: <err>"`. Status bar shows `↻` while `emailSyncing`. Bottom-bar `s` hint widens to `"sync (git+email)"` when enabled. When email is disabled all email cmds return nil so `tea.Batch` ignores them — the keybinding stays a single git-sync.
- **Telegram integration**: opt-in Telegram bot for mobile capture / browse / done, off until configured. `internal/telegram/` owns the integration; `cmd/telegram.go` registers `monolog telegram {serve,status}`. `internal/telegram/` MUST NOT import `internal/config` — values flow in via `config.Telegram() config.TelegramConfig` (`{Enabled, AllowedUserIDs, PullInterval, BrowseLimit}`) read once by `cmd/telegram.go` and passed by value to `telegram.Serve`. Config block is the optional `"telegram"` key in `<MONOLOG_DIR>/.monolog/config.json` (defaults: enabled=false, allowed_user_ids=nil, pull_interval=30s, browse_limit=20). `config.SaveTelegram` is the read-modify-write writer that preserves foreign keys (mirrors `SaveEmail`). **Secrets**: bot token comes from the `--token` flag on `monolog telegram serve` with fallback to the `MONOLOG_TELEGRAM_TOKEN` env var (flag wins; env is the recommended systemd path because `--token <value>` is visible in `ps aux`); `GIT_SSH_COMMAND` env points git at the host-local SSH deploy key. Token is never logged and never printed in `status` output (`status` only prints "set" / "unset"). **Bot abstraction**: `type Bot interface { GetUpdates(ctx, offset, timeout) ([]Update, error); SendMessage(ctx, chatID, html, kb) (msgID int, error); EditMessage(...); AnswerCallback(...) }` with neutral DTOs (`Update`, `Message`, `CallbackQuery`, `InlineButton`, `InlineKeyboard`) so tests fake the interface and the rest of the codebase never imports `github.com/go-telegram-bot-api/telegram-bot-api/v5`. `realBot` wraps `*tgbotapi.BotAPI`; `NewClient(token)` returns the production bot. **Capture** (free text from allow-listed user): `ParseCapture(text)` splits on first `\n` → first line title, rest body; `ParseInlineTags` extracts `#hashtag` tokens from the title (regex `#([A-Za-z0-9_-]+)`, deduped, hashtags stripped + whitespace collapsed). Body and inline `#hashtag` content survives untouched in the body. `store.Create` then applies the existing `tagname: <title>` prefix auto-tag rule against tags already on disk. Default schedule = today. **Browse**: `/today`, `/week`, `/active`, `/all` query `store.List` and send one message per task with inline buttons; `/all` is capped at `BrowseLimit` with a `<i>+N more — open laptop</i>` footer. Empty bucket replies with a single `<b>Today</b> — nothing 🎉` message. **Callbacks** (inline buttons, data format `verb:<ULID>`): `done:` runs `recurrence.CompleteAndSpawn` (writer=io.Discard; spawn warnings logged to opts.Writer) and edits the message to a strike-through row plus `↻ next: <date>` when a follow-up spawned; `active:` toggles the reserved `active` tag (add if absent, remove if present); `view:` swaps the summary into `FormatDetailView` (ID + Schedule + Tags + Recur + Created + Notes + body, 4096-char cap with `… (open laptop for full body)` truncation) with a `[⬆ Collapse]` button; `collapse:` reverses `view:`. ULID is full 26 chars in callback data so resolve is unambiguous; out-of-range / deleted IDs surface a toast (`"task not found"` / `"already done"` / `"invalid"`). **Reply=note**: any Telegram reply to a previously-sent task message extracts a task prefix from the replied-to text via `taskPrefixFromRow` — the first whitespace-bounded token that is not a **row marker** — calls `store.Resolve`, appends the reply text via `model.AppendNote`, and commits. Row markers are the state glyphs a rendered row can carry ahead of the `<code>` ULID prefix (`⭐` from `FormatTaskRow` when active, `✅` from `FormatDoneRow`); they are registered in the `rowMarkers` map in `handler.go` and skipped, since Telegram hands back the quoted row as plain text with the markers intact. **Any new glyph prepended ahead of the prefix in a row renderer must be added to `rowMarkers`**, or note-replies to that row variant silently fail to resolve. Ambiguous prefix surfaces `store.Resolve`'s error verbatim (HTML-escaped). **Access control**: non-allow-listed users are silent-dropped on plain messages; for callbacks the callback is answered with an empty toast (to clear the loading spinner) but no action runs. **Read-only on conflict**: if `git.Sync` fails after a local `git.AutoCommit`, the handler sets an `atomic.Bool` `readOnly` flag — subsequent write attempts (capture, done, active, note) reply with `⚠️ sync conflict, change not saved — resolve on laptop` and do NOT mutate the store; browse commands prepend `⚠️ <i>read-only — sync conflict pending</i>`. Any successful pull clears the flag — the background ticker or the pre-pull a command runs before serving it — so a `/today` or a button tap heals a stale conflict flag as readily as the ticker does. Because `handleBrowse`/`handleActive`/`handleAll` pre-pull *before* the banner is computed, a clean pre-pull also makes the `⚠️ read-only` browse banner disappear mid-command. **Sync orchestration** (`telegram.Serve`): a startup pull through `handler.pullOnce` (non-fatal; routed through `pullOnce` rather than `pullFunc` so it gets the same conflict recovery every other pull gets and stamps the shared freshness clock), then two goroutines — a `time.Ticker` pull-rebase ticker (interval = `cfg.PullInterval`) and a long-poll update loop calling `bot.GetUpdates(ctx, offset, 30s)`; updates handled inline (single-threaded write path via `sync.Mutex`); `ctx.Done()` shuts both down cleanly. Tests inject `pullFunc`/`syncFunc` to avoid real git operations. **Pull cadence** (three paths, one clock): the startup pull, the retained `runPullTicker` at `cfg.PullInterval`, and a freshness-gated pre-pull before every state-dependent command. `Handler.lastPull` is an `atomic.Int64` of unix nanos — deliberately *not* under `h.mu`, since the gate reads it from outside the lock — stamped by `recordPull` on **every** completed pull: `pullLocked` stamps it from a `defer` that fires on all exit paths (an errored pull still burned a round-trip, so the stamp is a rate limit, not a success ledger), and all three paths — startup, ticker, on-demand — go through it. The freshness question `pullFresh()` answers (`now.Sub(lastPull) <= commandPullMaxAge`, 5s, boundary counts as fresh) is asked **twice**: once in `pullBeforeCommand` outside `h.mu`, so a fresh clone costs a command neither a lock nor a fetch, and again inside `pullIfStale` **after** `h.mu` is taken. The second check is the load-bearing one — without it a command arriving while the ticker is mid-fetch waits out that fetch on the mutex and then immediately runs a second one, two fetch timeouts back to back, well past the few seconds Telegram allows before a tapped button stops spinning. `pullIfStale` also passes the shorter `commandFetchTimeout` (5s) where the ticker passes `git.DefaultFetchTimeout` (15s): a command has a person watching a spinner, and serving slightly stale tasks beats a button that appears to do nothing. `pullBeforeCommand` is the handler-side wrapper: **non-fatal** — a failed pull is logged to the `Serve` writer and the command is served from local state. Call sites: `handleBrowse` (`/today`/`/week`), `handleActive`, `handleAll`, once in `handleCallback` (covering all four verbs, placed before the `store.Resolve` lock — so a `done:`/`active:` tap on a `readOnly` bot pre-pulls *ahead* of those verbs' read-only guards, and a clean pull heals the flag), and `handleNoteReply` (after its `readOnly` guard). **`handleCapture` deliberately does not pre-pull** — a fresh ULID cannot conflict, `commitAndSync` already pulls after the write, and message-send is the most latency-sensitive path. The ticker is **retained** rather than replaced by the gate: it is the only thing that heals `readOnly` and retries stuck-rebase recovery while the bot is idle (a write-only conversation against a `readOnly` bot bails before pulling), and keeping it means `cfg.PullInterval` keeps its meaning with no config migration. The `internal/telegram` test package's `TestMain` defaults `pullFunc` to a stub returning an error — an error rather than nil, because a silently-succeeding default would clear `readOnly` underneath the tests that assert read-only behavior. **HTML rendering**: all titles/bodies pass through `html.EscapeString` before insertion into HTML templates; the only literal tags are `<code>`, `<i>`, `<s>`, `<b>`. URLs auto-linkify on the Telegram client (no `display.Linkify` OSC 8). **Deployment topology**: long-running `monolog telegram serve` on an always-on host the user owns — the reference deployment is a personal server (an old laptop / mini PC / Pi), with a small VPS or an EC2 t4g.nano as equally valid examples — holding its own clone of the tasks git repo; long-polling means no public HTTP endpoint, no webhook, and no inbound connectivity, so a box behind home NAT is a first-class host. `docs/deploy/` ships a systemd unit, `env.example`, and a README walking through host bootstrap (user creation, SSH deploy key, clone, systemd install). `make build-bot-linux BOT_ARCH=<arm64|amd64>` cross-compiles (aliases: `build-bot-linux-arm64`, `build-bot-linux-amd64`); `make deploy-bot DEPLOY_HOST=<user@host>` scps + restarts via SSH. `DEPLOY_HOST` must be a **login user with sudo**, not the `monolog-bot` service user (which is created with `/usr/sbin/nologin`). `deploy-bot` installs the binary as `$(BIN_DIR)/monolog` owned `root:root` mode 0755 — arch-neutral, so the systemd unit's `ExecStart` is portable across a Pi, an x86 box, and a VPS, and the service user cannot rewrite its own binary. `EC2_HOST` still works as an alias for `DEPLOY_HOST`. No webhook, no HTTP listener, outbound HTTPS only. The bot is just another monolog client — laptop side gains nothing new; the existing `s` sync + fsnotify watcher already handle the read side.
- **TUI auto-refresh on external changes**: the running TUI watches `<repo>/.monolog/tasks/` via `fsnotify` (debounced 250ms) and reloads when another process mutates the store — Raycast capture, a second terminal running `monolog add`, or an external `git pull`. `internal/tui/watcher.go` owns a small `taskWatcher` (channel + goroutine) constructed in `tui.Run`; failure to start (missing dir, OS limits) prints `monolog: watcher: <err>` to stderr and runs the TUI without auto-refresh, same precedent as `bootstrapExampleTheme`. `Model.watchCmd()` blocks on the watcher's channel and returns `externalChangeMsg{}`; the `Update` handler calls `reloadAll()` + `recomputeLayout()` and re-arms the cmd. **Reload is idempotent and unfiltered** — events from the TUI's own writes also fire, but `reloadAll()` is cheap and avoiding a race with self-mutations isn't worth the synchronization. No status flash on routine refresh (would be noisy under rapid external edits). `MONOLOG_NO_WATCH=1` is the escape hatch (mirrors `MONOLOG_NO_LINKS=1`); only `Write|Create|Remove|Rename` events trigger reload (chmod-only events are filtered as noise). Watcher is stopped via `defer w.Stop()` in `tui.Run`; the goroutine closes its channel on stop so `watchCmd` returns nil and the loop unwinds.
- **Redo (TUI)**: `ctrl+y` in normal mode re-applies the last undone action (multi-level, same 10-entry cap as undo) by calling `git.RevertSHA` on the revert commit from the prior undo — reverting the revert re-applies the original change. `Model.redoStack` ([]string, capped at `undoStackCap`) mirrors `undoStack`: each successful undo pushes the revert commit's SHA onto `redoStack` (via `taskSavedMsg.redoSHA`); `redoCmd()` pops and reverts that SHA, then pushes the new SHA back onto `undoStack` via `taskSavedMsg.redoneSHA` (which preserves `redoStack`, unlike the plain `sha` field) so `u` → `ctrl+y` → `u` cycles symmetrically. `restoreRedoSHA` mirrors `restoreUndoSHA`: on redo failure the SHA is pushed back onto `redoStack` from the main loop. Standard redo semantics: any new mutation (non-empty `taskSavedMsg.sha`) clears `redoStack`, since the prior redo history is no longer valid. The former `clearUndo` flag is renamed to `clearHistory` and clears **both** stacks — used by remote sync, since a rebase may rewrite SHAs referenced in either stack. Empty-stack guard in `updateNormal` shows "nothing to redo" without calling the goroutine.
- **Shared search ranker**: `internal/search/` owns all task ranking — one status-agnostic `Index` with **two entry points**. `Rank` is fuzzy (the query is one ordered subsequence over the candidate) and serves the TUI overlay and single-word CLI queries; `RankTerms` ranks a multi-word query by how many distinct query words a task actually contains, dropping zero-hit tasks, because `sahilm/fuzzy` matches a phrase as one ordered subsequence *including its spaces* — too lossy for a one-shot CLI query with no keystroke feedback. **TUI/CLI parity is therefore single-word only**; the full rationale and the mirrored parity tests are named on `RankTerms` in `rank.go`, not here. Two invariants are easy to break silently: `Len`/`Rank`/`RankTerms` are **nil-receiver safe** because `closeSearch` nils the index to release the task set while render paths keep calling them; and `NewIndex` stores titles/bodies **as-is, never pre-lowercased** — `sahilm/fuzzy` case-folds natively and a lowercased copy would misalign the `MatchedIndexes` byte offsets `highlightMatches` consumes (`RankTerms`' own lowercasing is safe: its terms feed a boolean `strings.Contains`, never an offset). CLI: `monolog search <query>...` with `-n/--limit` (default 10) and `-d/--done`, rendered by `display.FormatSearchResults` with untruncated titles and a `searchIDWidth = 12` ID prefix rather than `ShortID`'s 8 — 8 characters collide for tasks created within the same ~256 ms, and search IDs exist to be pasted into `monolog note <id>`. A residual collision surfaces as `store.Resolve`'s ambiguity error listing full ULIDs, never as a write to the wrong task.

- **Auto-push on mutation**: every commit a mutation makes is pushed to the remote, on by default — in a background goroutine in the TUI, synchronously after the success line in the CLI. `git.AutoPush(repoPath string, timeout time.Duration) (PushResult, error)` in `internal/git/autopush.go` is the whole algorithm: take `repoMu`; `IsRebasing` → return `ErrRebaseInProgress` and do nothing (a stuck rebase must be surfaced once, not retried on every keystroke); then `git push` via `runOut` under a `context.WithTimeout`. **Upstream handling**: `hasUpstream` (a bare `bool` from `git rev-parse --verify --quiet @{upstream}` — no output to parse, so no locale to be defeated by) decides between a plain `git push` and, when there is no tracking branch yet, `git push --set-upstream <remote> <branch>`. A repo whose remote was added by hand after `monolog init` therefore starts pushing on its first mutation instead of skipping in silence forever, which was the original "my tasks never reach GitHub" symptom wearing a different hat. `PushResult{Skipped: true}, nil` (silent, not a warning) is reserved for the cases with genuinely nothing to push to: no remote at all, a detached HEAD, or several remotes with no `origin` among them — `pushRemote` picks the sole remote or `origin` and returns `""` rather than guessing which of a user's remotes should receive their tasks. **Push first, rebase only on rejection** — a plain `git push` does not rewrite local history, so the TUI's undo/redo stacks stay valid in the common case; reusing `git.Sync` per mutation would wipe them on every keystroke and add a network pull to every mutation. A failure is **classified narrowly** by `isNonFastForward(out)` against the lowercased combined output (`non-fast-forward`, `fetch first`, and the branch-specific tails of the `updates were rejected because the …` hint — deliberately **not** a bare `! [rejected]`, which also covers `(stale info)`, `(would clobber existing tag)` and protected-branch declines that no rebase can fix, and deliberately not a bare `updates were rejected`, which git also prints for a tag clobber); anything else is returned unchanged with `Pushed: false` and **no** rebase, because the remote state is unknown. On a real rejection, `pendingTaskWrites` runs first: if any file under `.monolog/tasks/` is uncommitted **and its mtime is within `writeSettleWindow` (30s) of `start`, the wall clock captured at the TOP of `AutoPush` before it takes `repoMu`**, the rebase is **deferred** with an error wrapping `ErrRebaseDeferred` that names the offending paths and the remedy (`the next push commits it, or run 'monolog sync' now`) — the user has no other way to discover that a manual sync clears it. `repoMu` serializes git calls but cannot make a caller's `store.Update` → `AutoCommitSHA` pair atomic, and `--autostash` would stash that half-written task file — a conflicting pop writes conflict markers into the JSON that the pending `git add` then commits. A cycle of staleness is cheaper than a corrupted task. **Both halves of that check are load-bearing and were each a defect once.** The reference time is `start`, not `time.Now()` at the check, because `AutoPush` holds `repoMu` across its own push (and, on the rejection path, its fetch) while the writer is blocked in `AutoCommitSHA` on that same mutex — measuring at the check ages every pending write by the network I/O `AutoPush` itself imposed, so the writes it is delaying are the first to look settled, get swept into the `recover:` commit, and leave the writer's own commit failing with "nothing to commit" for a mutation that succeeded and reached the remote (in the TUI that also loses the SHA the undo stack needed). `writeSettleWindow` is likewise sized **above `DefaultPushTimeout + DefaultFetchTimeout`** for the same reason — `TestWriteSettleWindowOutlastsAPush` pins the invariant — and it is a `var` only so tests can shrink it. The comparison is **two-sided** (`age < window && age > -window`): a mtime in the reference time's future is the normal shape now (a write landing after `AutoPush` started) and is also what a skewed clock produces on a multi-device tool, and a one-sided `age < window` read that negative age as "in flight" until the wall clock caught up — permanent deferral again. Past the window on either side the file is an orphan. **The deferral is bounded and can never be permanent**: past the settle window nobody is mid-write, so the file is an orphan — a real task whose commit failed (every TUI mutation site returns `taskSavedMsg{err: "commit: …"}` after the store write already landed) — and `AutoPush` **commits** it (`recover: N uncommitted task write(s)`) instead of deferring again, then rebases and pushes it with everything else — but only after `partitionParsableTasks` has dropped any file that does not `json.Unmarshal` into a `model.Task`, since `store.List` errors out on the **first** unreadable task file rather than skipping it, so committing a truncated write (`store.writeTask` is a plain non-atomic `os.WriteFile`) would break `monolog ls`, the TUI and the bot on every device instead of only on the one that produced it. Skipped files are named in a warning carried alongside the push result, exactly like an autostash conflict, not returned as a failure. Deferring forever made auto-push stop working for good the first time an orphan appeared, silently reinstating the exact bug the feature exists to fix; losing the orphan is not an option either, so committing is the only safe direction. `pendingTaskWrites` parses the porcelain lines rather than testing them for emptiness (and returns the paths, which are handed straight to `git add`): an **untracked non-`.json`** entry (a `.DS_Store` from a Finder visit, an editor swap file — nothing in monolog's `.gitignore` excludes them) is skipped, because otherwise one stray file makes the guard true forever and auto-push can never recover from a diverged remote; an untracked `.json` still counts, since a concurrent `store.Create` looks exactly like that. Otherwise `pullRebaseResolving(ctx, repoPath, true, noPromptEnv, up)` runs (**`--autostash`** — `AutoPush` deliberately does not commit unrelated files, and the rebase refuses to run over a modified tracked file, which `applySettings` produces routinely by writing `.monolog/config.json` without committing it; `ctx` carries `DefaultFetchTimeout` so the network half cannot stall under the lock), and `res.Rebased` is set from its `Started` flag — true from the moment `git rebase` was invoked, **false** when the call died in the fetch, which rewrites nothing (an unreachable remote must not cost the user their undo history on every mutation). `up` is the `upstreamRef` computed above: on the no-upstream path it is carried into the rebase because a **rejected** `push --set-upstream` does not record the upstream it asked for, so an inferred rebase target there dies with `There is no tracking information for the current branch` and the repo can never push again. An **autostash conflict is a warning, not a failed rebase** (`errors.Is(err, git.ErrAutostashConflict)`): the rebase completed, the worktree is clean and the commit is on HEAD, so `AutoPush` carries the error as a warning, still runs the retry push, and returns it alongside `Pushed: true` (`errors.Join`ed with the push error if that also fails). Returning early there left the mutation unpushed until some later mutation happened to retry — the exact staleness this feature removes — over a conflict in `config.json`, which has nothing to do with it. Then **exactly one** retry push, no loop (another client can always race in again; the next mutation's push picks up where this one stopped). The retry's failure is wrapped as `push after rebase: %w` so callers can distinguish "could not push at all" from "rebased, then could not push". **`Rebased` survives the error return** and is the load-bearing contract for undo/redo: a plain push preserves both stacks, while a rebase clears them **even when the retry push then fails**, because the SHAs were already rewritten and `revertStackCmd` silently drops an entry whose `CommitSubject` misses. `repoMu` (`git.go`) is a package-level mutex around the mutating entry points (`AutoCommit`, `AutoCommitSHA`, `Revert`, `RevertSHA`, `Sync`, `AutoPush`), not a push-only lock: the coalescing design guarantees a mutation's `AutoCommitSHA` can run while a push is mid-rebase, which would either contend on `.git/index.lock` or commit onto a detached rebase HEAD. `PullRebase` and `Push` are **deliberately lock-free** primitives (`Sync` calls `Push` while already holding the mutex, and `PullRebase`'s only caller serializes under `internal/telegram`'s own handler mutex) — a future in-process caller such as a TUI pull ticker must take `repoMu` itself or route through `Sync`. Holding it costs latency, so **every network step under the lock is bounded**: the ceiling on a blocked mutation commit is two push timeouts plus one `DefaultFetchTimeout`, not "until ssh gives up" — the one exception being the interactive `Sync`, reachable only from the one-shot `monolog sync` process where nothing else contends (every in-process caller uses `SyncUnattended`). It is **per-process only**, and the cross-process failure mode is more than lock contention now: a Raycast capture, a second terminal or the Claude skill can each run their own `pull --rebase --autostash`, which moves HEAD and rewrites the worktree while this process is mid-commit — `index.lock` guards the index, not the rebase sequence. The cross-process failure mode is **silent data loss**, not a warning: while one process sits on a conflicted rebase another's `git add` still succeeds while its `git commit` fails (`Committing is not possible because you have unmerged files`), and the first process's `git rebase --abort` then resets index **and** worktree, deleting that staged file with no trace. `autoCommit` therefore **unstages the paths it staged when the commit fails**, which saves a *new* task file (it survives the abort as untracked, and the next push's `pendingTaskWrites` commits it) but not an uncommitted modification to a *tracked* one — abort hard-resets tracked paths, and nothing short of cross-process locking covers that. That residual window is the known, accepted cost. `sync.Mutex` is not reentrant, so shared work lives in unexported unlocked cores (`autoCommit`, `revert`). **Non-fatal everywhere**: a failed push never fails the mutation, never changes an exit code, and never rolls anything back; the commit is durable locally and the next push or `s` catches up. **Config**: `"auto_push": true` (written into `git.Init`'s config.json template) — `Load` reads it into an `AutoPush *bool` so an absent key keeps the `true` default while an explicit `false` disables; `config.AutoPush()` returns `false` when `os.Getenv("MONOLOG_NO_AUTOPUSH") == "1"` (exact `"1"` match, mirroring `MONOLOG_NO_LINKS`/`MONOLOG_NO_WATCH`; it is a kill switch only — `MONOLOG_NO_AUTOPUSH=0` cannot re-enable an on-disk `false`). `config.Save` is deliberately **not** an `auto_push` writer: it is already read-modify-write over a `map[string]any`, so the key round-trips, and writing the package var there would clobber an explicit on-disk `false` in any process where `Load` did not run. **CLI wiring**: `cmd/helpers.go` holds `var autoPushFn = git.AutoPush` (the test seam) and `pushAfter(w io.Writer, repoPath string)`, which no-ops when `config.AutoPush()` is false and otherwise calls `autoPushFn(repoPath, git.CLIPushTimeout)` (5s — a human is waiting on the process to exit; the TUI uses `git.DefaultPushTimeout`, 10s), warning a non-nil error to `w` and swallowing it — labelled `push failed: <err>` only when `res.Pushed` is false, since an autostash conflict comes back as an error *alongside* a successful push and calling that a failure sends the user chasing a task that is already on the remote. It also prints `Synced (auto-resolved N conflicts)` when `res.Resolved > 0`: a rejected push rebases, and `ResolveConflicts` settles a task-file conflict by keeping the newer `UpdatedAt` and **discarding** the loser, so staying silent there would let `monolog edit` drop a phone-side edit with no output at all — `monolog sync` and the TUI both report the same count. `pushAfter` sits **below** each command's success `Fprintf` (`add`, `edit`, `done`, `mv`, `rm`, `note`, plus `email sync`) — replacing `git.AutoCommit` with a combined commit-and-push in place would insert up to the full timeout of network I/O between the store write and the user-visible line, a visible hang in `monolog add` from Raycast or the Claude skill; this mirrors `cmd/done.go`'s archive-after-output ordering. **TUI wiring**: `var runAutoPush = git.AutoPush` is the seam, `Model.autoPushEnabled` is snapshotted from `config.AutoPush()` inside `newModel` (**not** threaded through `Options`, which would silently default it off for every test constructing `Options{}`), and `Model.autoPushCmd()` returns nil when disabled and nil-after-setting-`pushPending` when `pushInFlight` — **coalescing, not debouncing**, so a burst of mutations costs two pushes rather than one each. Three dispatch sites: the `taskSavedMsg` handler (batched alongside `archiveCmd` when `msg.err == nil` and any of `sha`/`redoneSHA`/`redoSHA` is set — undo and redo produce real commits too; the `restore*` fields are excluded because a *failed* revert creates no commit), the coalesced follow-up inside the `autoPushResult` handler, and the `emailSyncResult` handler (`email.Sync`'s batch commit is a seventh commit site that never produces a `taskSavedMsg`). The `autoPushResult` handler clears `pushInFlight` unconditionally so the gate cannot wedge shut, nils **both** stacks and does `reloadAll()` + `recomputeLayout()` when `rebased` **regardless of `err`**, flashes `push failed: <err>` (only when `msg.pushed` is false — otherwise `Synced; <warning>`, the autostash-conflict shape) / `Synced (auto-resolved N conflicts)` / `Synced`, and is **silent on plain success** (a flash would immediately overwrite the mutation's own `"Added: <title>"` — same rule as the fsnotify watcher). A `↑` in the stats bar while `pushInFlight` is therefore the only feedback that pushing happens at all; it needs no `autoPushEnabled` check of its own, since `autoPushCmd` returns nil before arming the flag. Quitting goes through `Model.quitCmd()`, which **flushes** an outstanding push (`pushInFlight || pushPending`) synchronously at `CLIPushTimeout` before returning `tea.QuitMsg`: coalescing parks the tail of a burst in `pushPending`, dispatched only when the in-flight result lands, so `d`,`d`,`d`,`q` used to drop it silently with no retry short of a later mutation or a manual `s`. `helpLine` runs both `m.err` and `m.statusMsg` through `Model.clampStatus`, which collapses whitespace and truncates to the terminal width: `recomputeLayout` budgets the help row exactly one line, and every error out of `internal/git` is multi-line (`runOut` appends git's full combined output), which auto-push turned from an `s`-only possibility into the default outcome of every offline mutation. Both the TUI push-failure status and the CLI's `pushAfter` warning go through **`git.ShortError(err)`** first: it drops git's `hint:` advice block (four lines telling the user to run by hand exactly what auto-push just did) and collapses the rest onto one capped line. It is deliberately **not** a first-line trim — `gitError`'s first line is the command and its exit status, and the diagnosis (`fatal: could not read Username…`) is on the second. `monolog sync` sets `SilenceUsage: true` and returns `errors.New(git.ShortError(err))` for the same reason: it takes no arguments and no flags, so a failure is never a usage error and cobra's help block only buries git's diagnosis. **Unattended-git hygiene** (`runOut` in `git.go`): `gitEnv` pins `LC_ALL=C`/`LANG=C` because the rejection classifier reads git's prose and a translated build would silently downgrade every rejection to an unrecoverable warning; `noPromptEnv` adds `GIT_TERMINAL_PROMPT=0` on the auto-push paths only, since git and ssh open `/dev/tty` directly and would otherwise write a credential prompt over the Bubble Tea alt-screen after every mutation (`monolog sync` and `monolog init` keep prompting — the user is at the keyboard); `cmd.WaitDelay` bounds the post-kill pipe wait so the context deadline is a real ceiling — but it bounds a **second, harmless** case too (a process that exits 0 while a grandchild still holds the inherited pipe, which `git-credential-cache--daemon` does for its 900s idle timeout), so `waitDelayAfterSuccess` treats `exec.ErrWaitDelay` with a successful `ProcessState` as success, or a push that reached the remote would be reported as `push failed: … WaitDelay expired before I/O complete`; and `redactCredentials` strips `://user:token@` out of every error before it reaches a terminal or the status bar, since git echoes the full remote URL back in `fatal: unable to access '<url>'` — its character class excludes `/` but **not** `@`, so the match runs to the last `@` of the authority (git accepts an unencoded `@` inside a password, and stopping at the first one leaks the tail). **Known gap**: this covers laptop → remote and (via the Telegram pre-pull) remote → bot; a task captured *in Telegram* still reaches the laptop only via `s` / `monolog sync`, since the fsnotify watcher sees local writes and auto-push only pulls when a push is rejected.
- **Shared rebase-with-resolution**: `pullRebaseResolving(ctx context.Context, repoPath string, autostash bool, extraEnv []string, up upstreamRef) (rebaseOutcome, error)` in `internal/git/git.go` is the single fetch → rebase → `IsRebasing` → `ResolveConflicts` → `RebaseContinue`/`RebaseAbort` block, shared by `Sync` (`autostash: false` — it commits everything first) and `AutoPush` (`autostash: true`), so the manual and automatic paths cannot drift on conflict semantics. Errors come back pre-wrapped (`pull: `, `resolve conflicts: `, `rebase continue: `, `autostash: `) and a resolution or continue failure aborts the rebase, leaving the worktree clean. **The resolve/`--continue` pair is a bounded loop, not a single round** (`maxRebaseRounds = 50`), because git stops a rebase once per conflicting local commit: two devices that each made two commits touching the same tasks — the ordinary case the auto-push feature targets — used to abort on the second stop and return an error that every later auto-push *and* `monolog sync` then reproduced identically forever, silently stranding the device with no visible breakage (abort leaves the repo clean). `Resolved` accumulates across rounds. A round is retried only while the repo is still mid-rebase **and** that round actually resolved something: `n == 0` means the next round would do the same nothing and fail the same way, so it falls through to `RebaseAbort` immediately rather than spinning under `repoMu`. `rebaseOutcome{Resolved, Started}` reports the conflict count plus whether `git rebase` was actually invoked — the flag `AutoPush` maps onto `PushResult.Rebased`, i.e. onto "the TUI must throw away its undo/redo stacks". **The rebase target is always named explicitly** (`upstreamRef.rebaseTarget()`: `<remote>/<branch>` when the zero value is filled in, otherwise `@{upstream}`), exactly as `git pull --rebase` does it: a bare `git rebase` cannot infer a target on a branch with no upstream, and git flips `--fork-point` **on** when no upstream argument is given, which can drop local commits if the upstream ref is ever rewound. **`--autostash` needs a post-check**: `git rebase --autostash` exits **zero** when the rebase succeeded but reapplying the stash conflicted, leaving unmerged index entries and conflict markers in the worktree while printing "Successfully rebased" — taken at face value that reports as a clean sync while every later commit fails with "Committing is not possible because you have unmerged files" and `monolog sync`'s `git add -A` stages the markers and pushes them to every device. `recoverAutostash` therefore inspects `unmergedPaths` directly after a successful autostash rebase and puts each path back exactly where it stood before the rebase: stage 3 (the stashed copy — the user's own uncommitted change) is written to the worktree and `git reset -- <path>` returns the index entry to HEAD, leaving an ordinary unstaged modification. It deliberately does **not** restore HEAD over the worktree: the only file that reaches here is `.monolog/config.json` (the settings modal writes it without committing), and discarding it silently reverted a setting the running TUI still showed as saved and had already confirmed — while the incoming version is *not* lost by keeping the local one, it is the committed HEAD version, one `git checkout HEAD -- <path>` away, which the returned error names. The error wraps `ErrAutostashConflict` so `AutoPush` can tell it apart from a failed rebase and still push; git's autostash stash entry is left in place as a backup rather than dropped. **The message is per-path, because one shape has no stage 3 at all**: a delete/modify conflict (the stash deleted the file, the incoming commit modified it) leaves only stages 1 and 2, so `gitShow(":3:")` fails and the only way to leave the repo committable is `git checkout HEAD -- <path>`, which **discards** the local change. `recoverAutostash` tracks those paths separately (`kept` vs `dropped`) and words each half truthfully — claiming "kept your uncommitted <file>" for a change that is no longer on disk sent the user looking for it — and every message ends by naming the autostash entry, which for a dropped path is the only remaining copy. Task files cannot reach that path — `pendingTaskWrites` commits or defers a pending task write before the rebase — so in practice it is `.monolog/config.json` changed on two devices. It is `git pull --rebase` **split in two on purpose**: the `git fetch` is the only network step and is bounded by `ctx` (killing a fetch is safe — it leaves no `.git/rebase-merge` behind), while the `git rebase` that follows is local and deliberately unbounded, because killing git mid-rebase would strand the repo in a state nothing in the package recovers from. `extraEnv` reaches the fetch only, since the rebase talks to nobody. **`Sync` vs `SyncUnattended`**: both call `syncRepo`, and they differ only in whether the caller can answer a credential prompt. `Sync` (only `monolog sync`) leaves prompting on and runs unbounded — the user is at the keyboard and can type a password or Ctrl-C. `SyncUnattended` (the TUI's `s` key and `internal/telegram`'s `syncFunc`) passes `noPromptEnv`, bounds the fetch with `DefaultFetchTimeout` and pushes through `pushWithTimeout`: Bubble Tea holds the tty in raw mode on the alt-screen, so git's `/dev/tty` prompt would be invisible **and** would hang holding `repoMu`, silently stopping every later mutation from committing. `AutoPush` passes `DefaultFetchTimeout` and `noPromptEnv`; the exported `PullRebase(repoPath string, fetchTimeout time.Duration)` — lock-free, used only by `internal/telegram` — is the same fetch/rebase pair, with the timeout supplied by the caller (`<= 0` falls back to `DefaultFetchTimeout`) so the bot can give an on-demand pull a shorter budget than its idle ticker. `runOut(ctx, dir, extraEnv, name, args...)` is `run`'s output-returning, context-aware sibling: it returns git's combined output on both paths so a push failure can be classified textually. `internal/telegram/sync.go#pullOnce` remains a **deliberate third copy** of the dance: it has its own injectable seams (`pullFunc`/`isRebasingFunc`/`resolveConflictsFn`/`rebaseContinueFunc`/`rebaseAbortFunc`), its own error strings, and its own `readOnly` side effects. Folding it in would need a seam-friendly shape and is out of scope.
